# PassWisely 截图输入：响应速度、准确率与链路提速点 · 2026-11-17

代码版本 `37f03b8`，生产环境（`passwisely.cn` gRPC → wise → Moonshot `kimi-k3.1-pro`，`reasoning_effort=low`）。只读测试，未改代码、配置、部署。

## 方法

- **题目**：`test/leetcode` 冻结的 20 道题（8 Easy / 8 Medium / 4 Hard）。
- **截图**：本地题面页按 Retina 全屏 3456×2234 截取，再用与安装包相同的 Electron 29.4.6 跑应用的 `prepareImageForModel` 逻辑，实际发送 1920×1241、质量 86 的 JPEG（平均 102 KB）。
- **链路**：加载生产 `ProcessingHelper.solveScreenshotProblemHelper`，经 gRPC 流式访问线上模型；只在 gRPC 流上加了旁路计时，不改变请求。每题串行请求一次，不重试、不挑最好一次。
- **判题**：仓库 `judge.py`，macOS 沙箱，Python 3.12.16，169 个固定用例 + 3 个边界用例。
- **对照**：6 道题各跑纯文本、1280 截图、1920 截图，交替执行，用于拆分图片带来的延迟。
- **服务端耗时**：wise 上 `passwisely-web` 日志里每个请求的耗时（中继收到请求到拿到上游响应头）。

不覆盖：真实屏幕捕获与系统权限、GUI 渲染时刻、真实 leetcode.cn 页面（含编辑器、导航等干扰）、多张截图、并发。每题只有一次采样。

### 其他观测

- **网络抖动**：Mac → `passwisely.cn` 的 gRPC 往返 P50 189 ms，P90 648 ms，最大 1033 ms。新建通道 P50 1.35 s，最大 3.3 s。
- **一次断流**：1249 题在 18.3 s 时内容停止，35.8 s 报 `Connection dropped`，已收到的 652 字符全部丢弃。服务端没有错误日志，当时相邻请求的往返在 600–730 ms，推测是客户端到 wise 的网络停顿触发 gRPC keepalive 超时（未证实）。
- **wise → Moonshot 新建连接**：TLS 完成 270–325 ms，一次 TCP 建连 1.1 s。
- **鉴权**：`/api/account` 服务端耗时 122–160 ms，是 4 次串行 Supabase 往返。
- **wise 负载**：2 核，测试时 load average 1.4–1.9。

## 可优化点（按预期收益排序）

| # | 优化点 | 依据 | 预期效果 | 改动范围 |
|---|---|---|---|---|
| 1 | 推理期间给出可见进度 | 首包 6.0 s 后服务端已在转发空 delta 的推理分片，客户端全部丢弃，用户要等到 13.8 s 才看到内容 | 首次反馈从 13.8 s 提前到约 6 s；总耗时不变 | 只改客户端即可显示“思考中”；要显示推理文本需改 proto 与中继 |
| 2 | 调整输出字段顺序，代码先出 | 代码在首段内容后 3.8 s 才开始；代码之后还有 3.6 s 的备选解法和题面摘要 | 代码提前约 3–4 s 出现；去掉或按需生成备选解法可再省约 1.5 s | 改提示词与流式解析；需回归准确率 |
| 3 | 评估更快的模型档位 | 推理占 40%，是最大单项；推理 token 速度只有可见输出的 60% | 取决于候选模型，未实测 | 配置项；需同题对比速度与准确率 |
| 4 | 本地 OCR，文本为主、截图兜底 | 纯文本首包 2.9 s，截图 5.6 s | 首包约省 2.7 s（约占总耗时 12%） | 客户端加 macOS Vision / Windows OCR；含图表的题需保留截图 |
| 5 | 中继内鉴权与扣费提速 | 桌面令牌先做一次必然失败的 Supabase 用户查询，再串行查会话、档案、余额、扣费 | 估计省 0.1–0.2 s | 会话短时缓存；非 JWT 令牌跳过用户查询；并行化 |
| 6 | 复用到 Moonshot 的连接 | 新建 TLS 270–325 ms，偶发 1.1 s | 估计省 0.3 s，并削掉尾部 | 中继侧保活或定时预热；需先埋点确认当前是否复用 |
| 7 | 启动和截图时预热 gRPC 通道 | 通道是惰性建连，代码里没有预连接；新建 P50 1.35 s | 只影响冷启动后的第一次请求 | 客户端调一次 Health |
| 8 | 断流后保留已收到的内容 | 1/20 请求在 36 s 后整体失败 | 不提速，减少最坏情况下的重来 | 客户端保留部分结果并提示续写 |
| 9 | 默认压到 1280 | 1920 → 1280 首包省约 0.4 s，token 少 45% | 速度收益小，主要省成本 | 一行配置；需验证小字号截图的识别率 |

第 5、6 项的数字是估计值：中继内 2.7 s 的基线目前没有分段计时。建议先在中继里按 requestId 记录“鉴权完成 / 扣费完成 / 上游连接 / 上游首字节”四个时间点，再决定这两项的优先级。

本地图片处理（约 0.3 s）和 gRPC 代理跳不是瓶颈，不建议投入。

## 追加：思考模式现状与“关闭思考”对比

### 现状

- 当前**思考是开启的**。`kimi-k3.1-pro` 官方文档写明 K3 系列始终推理、不能关闭，`reasoning_effort` 只有 `low / high / max` 三档，默认 `max`。
- 线上用的是最低的公开档位 `low`（`shared/kimi.ts` 在未指定时补 `reasoning_effort: "low"`，并删除 `thinking` 参数）。
- 实测发现一个**未公开**的取值：`reasoning_effort: "none"` 被上游接受，返回里不再有推理分片。它不在文档里，随时可能失效。

### 对比方法

同一批 20 张截图、同样的提示词，分别用 `none` 和 `low` 各跑一次，逐题交替先后顺序。gRPC 协议没有 `reasoning_effort` 字段，所以两组都走生产 HTTPS 流式中继（`/api/ai/chat/completions`），只有这一个参数不同。每题每档一次采样。

### 结果

| 指标 | 关闭思考 `none` | 当前 `low` |
|---|---:|---:|
| 请求完成 | 20/20 | 20/20 |
| 题目通过 | 17/20 | 19/20 |
| 用例通过 | 156/169 | 166/169 |
| 含边界用例的题目通过 | 16/20 | 19/20 |
| Easy / Medium / Hard 通过 | 7/8 · 7/8 · 3/4 | 8/8 · 8/8 · 3/4 |
| 首段可见内容 P50 | 7.7 s | 14.3 s |
| 代码完整 P50 | 15.5 s | 21.1 s |
| 全部完成 P50 / P90 / 最大 | 19.8 / 29.7 / 39.2 s | 24.2 / 33.2 / 68.5 s |
| 输出 token P50 | 376 | 507（其中推理约 158） |

- **时效**：逐题配对，关闭思考后首段内容中位数提前 5.9 s，完成时间提前 5.0 s（约 20%），20 题里 19 题更快。
- **首包没有变化**：两组模型开始输出前的等待都是约 7.6 s，关闭思考省掉的只是推理阶段。
- **准确率**：关闭思考多错 2 题。`none` 错了 2582 递枕头（Easy）、3644 排序排列（Medium）、2699 修改图中的边权（Hard）；`low` 只错 2699。加边界用例后 `none` 的 1372 还因 2000 层深树递归失败。
- **样本波动**：`low` 在下午的 gRPC 主测里是 16/19，这一轮是 19/20，单轮差 2 题在波动范围内。但 2582 这道简单题 `low` 在今天 5 次请求里全部通过，`none` 一次就错。

### 附带观测：无效取值会触发重度推理

第一轮对比因为我的脚本错误，把 `"none low"` 这样的无效字符串当作档位发了出去。20 次请求中 10 次在 90 秒超时，其余 10 次用了 27–65 秒，推理分片 450–2350 个（`low` 中位数约 160）。推测上游对不认识的取值回落到默认的 `max`。这一轮不计入上面的对比，消耗约 220 积分。

这也说明 HTTPS 中继会把客户端传来的任意 `reasoning_effort` 原样转给上游。

### 建议

不建议把默认档位改成 `none`：换来约 5 秒，代价是简单题也会出错，而且依赖未公开行为。可以考虑作为用户可选的“极速”档，默认仍用 `low`；真要上线，应先用更多题目重复采样确认准确率差距。

本节消耗：65 次请求，积分 10270 → 9594，共 676（含无效那一轮约 220）。

### 第 4 项：本地 OCR 为什么不采用

用系统自带的 Vision 文字识别处理同一批 20 张全分辨率截图（每张约 0.24 s，无需打包原生程序）：

- 方法签名完全正确的只有 8/20。典型错误：`List[int]` 识别成 `Listlint］`，`coordinate1` 识别成 `coordinatel`，`longestZigZag` 首字母被改成大写。
- 题面逐字完全正确的只有 3/20，字符召回率平均 97.2%、最低 83.7%。“无解返回[]”被识别成“无解返回口”，“1≤target”被识别成“1starget”。

视觉模型直接读截图时 19/19 都读对了。用 OCR 文本替代截图，换来的约 2.7 秒首包会以方法名和约束出错为代价，所以没有接入。原型和识别结果保存在结果目录的 `ocr-evaluation/`。

### 第 3 项：为什么没有实测

共享 Key 的请求由服务端强制使用后台配置的默认模型，客户端选不了别的模型。要实测 highspeed，需要先部署本次改动，然后二选一：把后台默认模型临时切到 highspeed（影响所有用户），或提供一个 Moonshot 个人 Key 走自带 Key 通道。另外积分仍按 K3 的现有策略扣，highspeed 的上游价格需要负责人确认。

### 上线注意事项

- **部署顺序**：先部署服务端（网站中继 + desktop-api），再发布客户端。旧客户端与新服务端、新客户端与旧服务端都兼容；后一种组合下极速档不生效。
- **systemd 单元有改动**：`passwisely-desktop-api.service` 新增 `PASSWISELY_KIMI_PREWARM=1`，需要重新执行激活脚本（含 sudo）才会生效。不重装单元时连接池仍然工作，只是没有预连接。
- **Kimi 上游路径变了**：默认 Key 的 Kimi 请求现在经 `127.0.0.1:3013` 的 Node 进程转发。该进程不可达时自动回退到直连。
- **验证方法**：上线后在 `journalctl -u passwisely-web` 里查 `ai_chat_timing`，每个请求一行，含鉴权、配置、扣费、上游响应头四个时间点；`journalctl -u passwisely-desktop-api` 无需额外配置。
- **中继现在会拦截档位**：共享 Key 的请求只接受 `none` 和 `low`，其他取值一律按 `low` 处理，修掉了上一节发现的“任意档位被原样转发”问题。
- **极速档依赖未公开行为**：`none` 不在 Kimi 文档里。如果上游改为拒绝它，极速档会报错，需要把 `shared/kimi.ts` 里的 `KIMI_FAST_EFFORT` 改回 `low`。

## 追加：默认模型改为 kimi-k3.1-pro-highspeed

按负责人决定，代码里的默认 Kimi 模型从 `kimi-k3.1-pro` 改为 `kimi-k3.1-pro-highspeed`（`shared/kimi.ts`、桌面端模型列表、两份 `.env.example`）。`kimi-k3.1-pro` 仍可选。

- **这个模型没有实测过**：速度、准确率、是否接受 `reasoning_effort: "none"`、上游价格都未验证。本报告里的所有数据都来自 `kimi-k3.1-pro`。
- **线上不会因为这次提交自动切换**：共享 Key 请求使用的模型来自 Supabase 里的后台设置 `ai_default_model`，代码默认值只在该设置缺失或数据库不可用时兜底。要让线上用 highspeed，需要在部署后到管理后台把“模型型号”改为 `kimi-k3.1-pro-highspeed`。
- **必须先部署再改后台设置**：当前线上代码不认识 highspeed，会把客户端的 `temperature` 等参数原样发给上游（K3 系列对这些参数取固定值，传别的值会报错），并按每次 1 积分的固定价扣费。
- 切换后建议用 `test/performance/results/2026-11-17-screenshot/scripts/` 里的脚本重跑 20 题，对比本报告的基线。
