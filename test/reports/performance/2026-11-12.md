# PassWisely 性能与质量测试 · 2026-11-12

已完成当前本机网络状态下的实测：20 道纯文本题、169 个固定用例及 3 个补充边界、3 道截图题、3 道 HTTPS 流式对照、60 次有效网络探测、6 条不同合成语音各两次回放，以及 65 项相关回归。Astrill 全程保持原状；用户明确要求不切换，因此本轮不能给出 VPN 开关造成的差值。

**环境与执行边界**

本机 Apple M5 Max、18 逻辑 CPU、36 GiB 内存；安装的 PassWisely 2.0.0 提供 Electron 29.4.6 / Node 20.9.0 arm64 运行时。测试加载生产 TypeScript 管线，52 个 desktop/shared/proto 文件与 r7 冻结源代码逐字节一致。安装包 ASAR SHA256：`e9a4dd0d053aef04875cd150eb8c6fd83ff25649062de11b69c97d8cc7c3f2d3`。这不等于对原生 GUI 或完整安装包的全量实测。

客户端默认 `.cn` 直达 Wise；`.com` 官网在 47.95.66.86，再转发 API 到 Wise。线上共享模型配置只读核对为 `kimi-k3.1-pro`，没有更改模型、价格、部署、VPN、代理或 DNS。仅为原测试账号创建了本轮临时会话，现已撤销并以 401 响应核验，其他登录记录未修改；没有人工充值或退款。

Astrill 版本 3.10.0.3073，相关进程存在，系统探测中 HTTP/HTTPS 系统代理关闭，目标路由接口为 en0。这些事实不能证明某个应用是否实际经过 Astrill；当前连接模式、节点和按应用路由未获确认。所有结论均限定在本轮保持不变的网络状态。

**网络与 VPN 判断**

每项 3 次新建连接、7 次复用连接；下表是相应批次的样本中位数。HTTPS 测首字节，gRPC Health 测完整往返，不混入模型生成时间。

|探测|.cn 新建|.cn 复用|.com 新建|.com 复用|
|---|---:|---:|---:|---:|
|首页 HTTPS|320 ms|95 ms|58 ms|21 ms|
|账户 HTTPS|478 ms|228 ms|617 ms|481 ms|
|gRPC Health|376 ms|86 ms|392 ms|367 ms|

60/60 有效探测均成功，没有观察到 fetch failed 或超时。`.com` 的复用 gRPC Health 比 `.cn` 约多 281 ms，符合多一段中转的方向，但本轮未做逐跳分段计时，不能将全部差异归因到某一跳。客户端当前已默认 `.cn`，无需为本轮测试切换域名。

**VPN 结论：不能量化 Astrill 的因果影响。** 没有关闭 VPN 的同网同题对照，也未验证各进程的实际隧道路由。当前网络往返在几十至数百毫秒，首个模型内容却需约 9.55 秒，且本地与服务端 CPU 较低；据此推断，当前主要优化目标在服务端处理/上游推理等待。不能把剩余时间全部精确认定为上游模型耗时，仍需鉴权、数据库与供应商分段埋点。

若后续获准对照，应固定网络和节点，按 ABBA 顺序交替 VPN 状态，使用相同请求并重复，记录 token 长度、输出差异和服务器负载。本轮没有执行该实验。

**截图与语音**

截图使用简单、中等、困难题各一张，生产识题/解题代码真实访问线上模型；完整耗时分别 13.32、22.65、30.84 秒，三份代码均通过测试，识别题面未保留浏览器导航或 PassWisely 控件文字。只观察生产解析器的进度发布，没有测用户实际看到内容的渲染时刻。辅助 HTTPS 与截图批次同时运行，最多两条模型请求；不将其耗时当作与串行主批次的严格传输 A/B。

语音使用已有 Tingting 与本机 Samantha 合成文件，直接连接官方 Deepgram WSS，复用生产配置和 normalizer。每条回放两次，之间 12 秒暂停、KeepAlive、恢复、Finalize、CloseStream；6 条连接均保持存活，暂停期间发送音频字节为 0，最终正常关闭。它覆盖 Intel 直连传输的合成文件路径，没有测试真人、麦克风/系统来源、Apple Silicon Recall 全链路。

纯文本测试进程总耗时 372.73 秒，CPU 1.74 秒，峰值 RSS 142.7 MiB。该进程包含 TypeScript 测试加载器，不包含完整 Electron GUI/GPU/音频采集，不能充当应用总内存。

|Wise 服务|30 秒采样 CPU / 秒|占单核百分比|观测峰值 cgroup 内存|
|---|---:|---:|---:|
|passwisely-web.service|0.808|2.68%|418.9 MiB|
|passwisely-desktop-api.service|0.144|0.48%|40.3 MiB|

两项服务的 MainPID 在采样期内稳定；cgroup 内存包含缓存，不是进程 RSS。在这个小负载窗口未见资源饱和证据；它不建立并发容量、无内存泄漏或长期稳定性的结论。65 项会话、流处理、权限和原有回归测试均通过，测试在延迟采样完成后运行。

**下一步优先级**

|优先级|工作|验收方式|
|---|---|---|
|P0|中文转录准确率、重要数字/术语校验、低置信度提示及快速修改|建立至少 100 条授权真人语料，固定 CER、术语召回与数字正确率；按错例评测候选引擎|
|P1|缩短首个可用内容等待，提供短提示与完整解答两档|同题重复评估高吞吐候选模型；建议目标首内容 P50<5s、P95<12s，准确率与完整性不得下降；这些是目标而非已实现|
|P1|增加按 requestId 关联的鉴权、数据库、供应商首字与前端阶段耗时|能定位每条慢请求，区分生成失败、传输失败、截断和内容错误；先不扩容|
|P2|维持 .cn 直连和复用连接，扩大题库、实机与稳定性覆盖|至少 200 道分层题、大输入性质校验、Intel/Windows 实机及长期稳定性单独验收|

当前已经使用流式响应，K3 推理强度也已设为 low。K3 始终推理，不能把“关闭 thinking”当作可用提速开关；`kimi-k3.1-pro-highspeed` 可作为下一轮候选，但尚未实测，不能承诺更快或准确率不变。[Kimi 官方参数说明](https://platform.kimi.com/docs/api/models-overview)。连接复用属于现有能力，本轮结果支持继续保留；gRPC 官方也建议复用 channel/stub。[gRPC 性能建议](https://grpc.io/docs/guides/performance/)。
